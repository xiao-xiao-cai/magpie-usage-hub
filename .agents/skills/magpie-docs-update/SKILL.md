# 项目文档更新规范

## 默认规则

- 先用一句话回答“谁看完后要做什么”，再选一处主说明。同一字段、流程或约定在主说明维护细节，其他入口只保留读者需要的结论和链接。
- 写清哪些是设计约定、哪些已实现、哪些已在指定版本和形态验证。用源码或清单核对接口，用实际运行结果支撑“已支持”。示例使用合成数据。

## 按文档类型选写法

| 主说明与读者 | 怎样组织正文 | 写完如何判断够用 |
| --- | --- | --- |
| [README.md](../../../README.md) · 首次访问者 | 先说插件解决什么问题、当前能用到什么程度，再给最短的上手路径和按任务组织的链接。设计阶段把读者引向功能规格与已有验证。 | 新读者能判断是否适用，以及第一步去哪里。列出的安装或使用方式有可用入口。 |
| [AGENTS.md](../../../AGENTS.md) · 仓库开发者和 Agent | 把开发约定写成“何时 → 做什么 → 如何验证”。任务路由采用“任务 → Skill 或主文档”，说明适用边界。 | 给出一项改动，能由此选中规范、找到实际入口并判断何时结束。 |
| [功能规格](../../../docs/01-插件定位与功能规格.md) · 产品读者与实现者 | 按使用者、触发条件、可观察结果写需求。给容易混淆的范围一个具体例子。 | 读者能用一个场景判断该功能是否满足需求，并定位验收依据。 |
| [开发基线](../../../docs/02-开发基线与兼容性.md) · 接入或升级维护者 | 按版本和运行形态列出接口约定、已有证据与待验能力。附对应版本来源。 | 一项 CLI、Web 或桌面结论能追溯到具体版本与观察。 |
| [架构](../../../docs/03-整体架构与模块职责.md)与[恢复设计](../../../docs/05-同步流程与故障恢复设计.md) · 后端实现者 | 架构沿一条真实调用链写模块职责、数据流和状态归属。恢复按“故障点 → 持久状态 → 重试动作 → 恢复结果”写，跨进程时画时序图。 | 能指出谁决定推进游标，以及中心已接收、本地未落盘时从何处重放。 |
| [网关接口与字段规范](../../../docs/04-网关接口与用量数据规范.md) · 调用方 | 先给请求方法、路径、鉴权与响应，再用表说明字段类型、单位、必填与缺失语义。用最小合成样例说明正常和失败结果。 | 调用方能构造请求、解释返回值，并区分已计价的 `0` 与缺少价格。 |
| [配置与诊断](../../../docs/06-配置与诊断页面设计.md) · 管理员与页面开发者 | 配置项写用途、单位、校验、默认或建议值、生效时机。诊断按“看到什么 → 意味着什么 → 可以做什么”组织，注明 Web 和桌面差异。 | 管理员能区分“已保存”和“后台已生效”。例如 `pollIntervalSec` 的 60 秒是建议值，实际缺省值需查解析器，调度生效需有运行证据。 |
| [开发指南](../../../docs/Magpie插件开发指南.md)与[部署运维](../../../docs/07-部署接入与运行维护.md) · 动手操作的人 | 教程从隔离环境和最小示例开始，每一步给命令、执行位置和预期输出。运维按真实角色写前提、操作、成功信号和失败后的恢复办法。 | 读者知道命令在哪一端运行，并能凭观察结果决定继续或恢复。 |
| [开发阶段与验收](../../../docs/08-开发阶段与验收计划.md) · 验收者 | 阶段目标写成可观察的通过条件。验证记录单列级别、版本与形态、实际操作、预期与观察结果、待验项。 | 计划中的用例与已经跑过的用例清楚可辨。只列本次改动涉及的级别和场景。 |
| [开源准备](../../../docs/GitHub开源准备.md) · 发布维护者 | 按发布范围、前置条件、操作顺序、结果核对写检查项，注明哪些远端操作需要授权。 | 每项能据实判断是否完成，执行发布仍按单独授权进行。 |
| 根目录 `plan/` 的执行计划 · 本次任务执行者 | 写目标、步骤、依赖和每步的完成条件。任务产生的长期结论归入对应的 `docs/` 主说明。 | 执行者能接着做下一步。公开导航链接指向随仓库交付的文档。 |

## 何时更新相关文档

任务开始时对照下表选出受影响的文档。每当本轮工作产生新的决定、实现或验证结果，就更新对应段落。同一事项可以更新多次，例如先写配置的设计值，实现后核对实际缺省值，实测后再补生效时机。

| 触发事件 | 更新哪份文档、在什么时候写 |
| --- | --- |
| 需求、采集范围或验收标准确定或调整 | 在据此开发前更新功能规格（01）的范围和预期结果，以及阶段验收（08）中受影响的通过条件。讨论中的候选方案留在任务计划。 |
| 目标版本、模块职责、接口或恢复策略确定 | 目标版本选定时更新开发基线（02）。方案确认时按影响更新架构（03）、网关契约（04）或恢复设计（05）的设计约定。实现若与已确认设计有出入，先核实差异，在本次交付前对齐实际行为与说明。 |
| 配置、页面流程或用户可见行为发生变化 | 交互方案确认后更新配置与诊断（06）的预期流程。解析器、页面或调度器改动落地时核对字段、提示和恢复操作。若修复使行为重新符合现有说明，保留该说明，复验后更新受影响的验收记录。 |
| 开发命令、部署前提、权限或运维步骤改变 | 改动落地时同步插件开发指南或部署运维（07），在开发者或运维人员按新步骤操作前更新示例。命令及恢复步骤的实测结果在对应环境复验后补入。 |
| 完成一次定向验证、发现回归或修复后复验 | 取得结果时更新阶段验收（08）中受影响的场景，记录版本、形态、实际结果和待验项。若旧结论已失效，同步修正基线或使用说明中引用该结论的段落。 |
| 首次公开的候选内容或发布状态变化 | 候选版本、许可或公开范围确定后，在发布操作前更新开源准备清单。实际公开、发布或上传的结果在操作完成并回读后填写。 |
| 本地任务启动、遇到阻塞或完成步骤 | 使用 `plan/` 的任务在开工时记下目标与步骤，依赖、进度或完成条件变化时更新计划。结项时将已确认且需长期维护的结论同步到相应主说明。 |

## 同步 README.md 和 AGENTS.md

在确定改动范围时标出两个根入口中受影响的段落。主说明移动或更名时，在同一次改动中修复导航。开发约定开始采用时更新 AGENTS.md，支持形态取得验证后更新 README.md 对该形态的可用性说明。**同一任务交付前**逐一核对两个入口。

| 变化 | README.md 检查点 | AGENTS.md 检查点 |
| --- | --- | --- |
| 功能可用性、支持形态、安装或配置方式变化 | 更新项目状态、用户操作和上手入口。 | 更新受影响的开发基线、调试命令或验收要求。 |
| 新增、重命名或调整 Skill，改变目录规则、测试或开发流程 | 若“从这里开始”的入口或面向读者的说明受影响，修正对应行。 | 更新“任务 → Skill”路由、适用边界及相关操作规则。 |
| 新增、移动、合并或删除主文档 | 更新相关读者导航。 | 更新相关开发导航。同时检查功能规格中的开发参考索引和旧路径的其他引用方。 |
| 修正措辞或内部重构 | 核对公开行为与入口是否仍准确。 | 核对开发操作与验证方式是否仍准确。两处均准确时，按原文保留。 |

## 交付检查

1. 对照本次改动核对主说明中的示例、命令参数、路径和证据。若主文档改名，在仓库中搜索旧文件名和旧标题，检查直达链接和纯文本指引。
2. 链接有变化时，从项目根目录用[链接检查脚本](scripts/check_local_links.py)检查两个入口、主说明和实际引用方。以下以调整配置文档入口为例。`uv` 按脚本声明准备依赖。

   ```powershell
   uv run --script .agents/skills/magpie-docs-update/scripts/check_local_links.py --root . README.md AGENTS.md docs/01-插件定位与功能规格.md docs/06-配置与诊断页面设计.md
   ```

3. 修复缺失目标，单独核对有变化的章节锚点、外部来源和 HTML 链接。纯文档改动在 L0 足以验证陈述及入口时结束。

## 输出格式

`读者与任务 | 主说明 | README.md / AGENTS.md 各自的更新或核对结论 | 验证与待验项`。入口无需修改时，简述仍准确的原因。

## Gotchas

- 手册写“已支持”之前核对对应形态的证据。临时 CLI 能加载不能证明 Web 交互、桌面或无人值守运行正常。
- 相对链接从引用它的文档所在目录解析。`plan/` 由 Git 忽略，本机存在的计划文件可能通过本地链接检查，却无法由仓库读者打开。
