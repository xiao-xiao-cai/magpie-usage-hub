# 部署接入与运行维护

在 Linux 原生或 Docker 运行的中心 Magpie 安装 Usage Hub `0.7.0`。Windows 使用 Magpie 内置的可观测性设置经 WireGuard 上报。接口核对基线为 Magpie `v0.1.4799`，Linux 原生中心的接入版本为 `v0.1.4947`。[开发基线](02-开发基线与兼容性.md) · [原生 OTLP 验收](08-开发阶段与验收计划.md#原生-otlp-接入验收)

## 中心安装与接收

从仓库根目录运行 `npm pack --ignore-scripts` 生成 `magpie-usage-hub-0.7.0.tgz`。使用归档中的 `package/` 目录注册插件。已有中心先按[升级与回退](#升级与回退)保留备份。

### Linux 原生中心

1. 在服务器上确认现有 Magpie systemd 服务及运行账号，记录服务实际使用的 `HOME`、`XDG_CONFIG_HOME` 和 `XDG_CACHE_HOME`。用该服务实际执行的二进制检查 `magpie --version`。同一个 `magpie serve --web` 进程运行 Web 与中心回环网关，页面服务 `3493` 保持回环，由已登录的 Web 代理访问。
2. 准备服务账号可读写的持久目录。在使用相同账号、二进制和配置环境的终端解包并注册。用实际解包目录替换示例路径，注册到包含 `package.json` 的 `package/`。服务账号也须能写入配置目录下的 `magpie-usage-hub/`。

   ```sh
   tar -xzf magpie-usage-hub-0.7.0.tgz -C /srv/magpie/plugins/usage-hub
   magpie plugin add /srv/magpie/plugins/usage-hub/package
   ```

3. 确认 WireGuard 接口已取得接收地址，并让接口在 Magpie 服务前就绪。使用 `wg-quick` 管理示例接口 `wg0` 时，可在 Magpie 服务的 systemd drop-in 设置以下依赖，服务名按实际配置调整。

   ```ini
   [Unit]
   Requires=wg-quick@wg0.service
   After=wg-quick@wg0.service
   ```

4. 在主机入站防火墙 `INPUT` 链仅允许从 WireGuard 接口、已登记对端地址进入的 `3494/tcp` 流量。接入设备时将中心监听 IP 设为服务器实际 WireGuard 地址，插件会直接绑定所填端口。

### Docker 中心

1. 确认 Compose 服务、Magpie 配置卷和容器内 `magpie --version`。在持久卷解包，在中心容器运行 `magpie plugin add /config/plugins/usage-hub/package`，路径换成实际包含 `package.json` 的目录。
2. 桥接模式在接入时将中心监听 IP 设为 `0.0.0.0`，并在 Compose 中将端口仅发布到服务器 WireGuard 地址。将示例 `192.0.2.2` 换成实际地址，设备访问地址使用该宿主地址。宿主网络模式直接监听实际 WireGuard 地址。沿容器的实际入站路径按 WireGuard 接口和已登记对端地址限制 `3494/tcp`。

   ```yaml
   ports:
     - "192.0.2.2:3494:3494/tcp"
   ```

### 接入第一个来源

1. 登录中心 Magpie Web，打开 **Magpie Usage Hub**。全新安装默认显示中心本机用量。保留中心默认回环网关，或从「配置 → 中心设置」核对网关与时区。[设置字段](06-配置与诊断页面设计.md#options-与宿主校验)
2. 在 Windows 生成令牌摘要，从首页「配置来源」或「配置 → 来源管理 → 添加设备」填写设备信息。首次添加同时填写中心监听 IP 和端口、Windows 可访问的基础地址。默认接收端口为 `3494`。使用 HTTPS 时由反向代理终止 TLS，Windows Magpie 校验证书与主机名。[Windows 上报配置](#windows-上报配置)
3. 保存后确认向导显示 Windows 填写说明。Linux 原生中心可用 `ss -lntp` 核对网关和 `3493` 的回环监听及 `3494` 的 WireGuard 监听。Docker 中心分别核对容器监听与宿主转发。确认只有获准对端可连接接收端口。后续在「添加设备」复用接收设置。[端口职责](03-整体架构与模块职责.md)

## Windows 上报配置

1. 接通 WireGuard。Windows Magpie 网关继续使用本机回环，例如 `127.0.0.1:3425`。若 Windows 管理了出站白名单，放行至中心的地址和接收端口。
2. 每台设备生成独立的 32 字节随机令牌。在同一个 PowerShell 会话执行以下命令，将输出的 SHA-256 摘要填入中心的「添加设备」向导。中心监听启用后，用实际地址执行 `Test-NetConnection -ComputerName 192.0.2.2 -Port 3494`，确认 `TcpTestSucceeded` 为 `True`。

   ```powershell
   $usageHubBytes = New-Object byte[] 32
   $usageHubRandom = [Security.Cryptography.RandomNumberGenerator]::Create()
   try { $usageHubRandom.GetBytes($usageHubBytes) } finally { $usageHubRandom.Dispose() }
   $usageHubToken = [BitConverter]::ToString($usageHubBytes).Replace('-', '').ToLowerInvariant()
   $usageHubHash = [Security.Cryptography.SHA256]::Create()
   try {
       $usageHubDigest = [BitConverter]::ToString($usageHubHash.ComputeHash([Text.Encoding]::ASCII.GetBytes($usageHubToken)))
   } finally { $usageHubHash.Dispose() }
   $usageHubDigest.Replace('-', '').ToLowerInvariant()
   ```

3. 在 **Windows Magpie** 打开「设置 → 可观测性（Observability）」，按下表填写。将以下命令生成的请求头粘贴到 `OTLP headers`，确认保存后开启 `OTLP export`。Magpie 会在基础地址后追加 `/v1/traces`。[原生设置与环境变量](https://github.com/yetone/magpie/blob/v0.1.4799/docs/reference.md#L4397-L4421)

   ```powershell
   "Authorization=Bearer%20$usageHubToken" | Set-Clipboard
   ```

   | Magpie 字段 | 取值 |
   | --- | --- |
   | `Collector` | `OTLP`。 |
   | `OTLP endpoint` | 中心接收基础地址，例如 `http://192.0.2.2:3494`。 |
   | `OTLP headers` | `Authorization=Bearer%20<本机令牌>`。中心登记的是摘要。 |
   | `Export metrics` | `Off`。本实现接收逐条 trace。 |
   | `Request and response content` | `Metadata only`。 |
   | `Trace agent conversations` | 需要受支持的本机会话用量时开启。会话与网关各自有覆盖范围，查询可按分项筛选。 |

4. 保持 Windows Magpie 及本机网关运行。让网关处理一条新请求，再在中心「配置 → 来源管理」核对「已收到用量」和「最近接收」。回看板按该来源和原调用时段核对模型及 Token。要验证会话分项，允许 Magpie 读取对应客户端的本机会话，再完成一条新调用。例如 Codex 可执行 `magpie sessions read on codex`，并在中心切到「会话」。[原生会话覆盖](https://github.com/yetone/magpie/blob/v0.1.4799/docs/reference.md#L4488-L4529) · [统计口径](04-网关接口与用量数据规范.md#怎样解释中心统计)

Windows 原生导出会重试部分失败，成功送达的迟到记录按原调用时间入桶。启用前的记录、队列溢出或重试耗尽的批次不会自动补齐。中心保留已入库历史。[原生导出队列与失败处理](https://github.com/yetone/magpie/blob/v0.1.4799/docs/reference.md#L4593-L4605) · [故障处理](05-同步流程与故障恢复设计.md#故障处理)

## 日常维护

- **连接排查。** TCP 不通时检查 WireGuard 和中心监听。Linux 原生中心核对 systemd 启动顺序与主机 `INPUT` 链。Docker 中心核对实际转发路径与防火墙，桥接时核对 Compose 端口发布。TCP 正常时，检查 Windows Magpie 的 OTLP 开关和 endpoint，核对请求头里的令牌与中心登记的摘要，确认来源已启用。一次完整验证以中心出现本次新调用为准。
- **令牌轮换。** 在中心为原来源登记新摘要，在 Windows 更新 `OTLP headers`。完成一条新调用，中心显示新凭据已验证后撤销旧凭据，历史仍归同一来源。[来源管理](06-配置与诊断页面设计.md#来源管理)
- **中心备份。** 数据库位于 `<Magpie 配置目录>/magpie-usage-hub/push/center.sqlite`，保存来源、凭据摘要、用量和中心本机游标。采用 SQLite 一致性备份，或停写后备份实际配置目录或配置卷。恢复时核对备份点之后的凭据撤销及轮换记录，再恢复接收。备份点之后仅在中心存在的 OTLP 历史不会由发送端自动重放。[故障处理](05-同步流程与故障恢复设计.md#故障处理)

## 升级与回退

1. 在维护窗口停止旧中心的采集与接收。保存旧包、插件注册、Options、中心 SQLite 一致性快照、配置目录或配置卷，以及实际服务和防火墙配置。曾在 Windows 启用旧版 Usage Hub 上报时，先停用该插件。`0.6.0` 的中心本机游标和已发布的远程历史随 SQLite schema 升级保留。`0.5.0` 的 `pull/` 配置和 `v0.4.0` 的账本仍在各自的路径。[旧版本接入说明](https://github.com/xiao-xiao-cai/magpie-usage-hub/blob/32abba84584f302168f42facd84cf126cea69387/docs/07-部署接入与运行维护.md)
2. 在中心的 Magpie 服务账号和配置环境中，或在对应的中心容器内，用 `magpie plugin list --json` 核对已注册的 `spec`。沿用本地路径时，停写后把目录内容整体换成新包的 `package/`，再用同路径执行 `magpie plugin add` 以保留原 Options。改用新路径或从 npm 注册切换时，记录原设置，用 `magpie plugin rm "<旧 spec>"` 移除旧注册，注册新目录并重新保存设置。迁移中心运行形态时，让目标服务使用迁移后的配置与同一备份时点的中心状态，核对服务账号对状态目录的读写权限。[中心安装与接收](#中心安装与接收)
3. 启动目标中心，核对插件已采用当前修订、旧历史可查和中心本机游标可续读。若网关变更导致游标需重建，先核对网关归属与原生历史范围。沿用已有 OTLP 来源时验证来源与凭据读回，首次启用原生 OTLP 时为 Windows 登记新来源。记录切换时间，验证 Windows 的 Magpie 回环和到中心 `3494` 的出站。若曾为中心拉取增加 Windows `3425` 的项目专用入站规则，按备份恢复此前的入站状态，验证中心至 Windows `3425` 的项目访问已关闭。[游标恢复](05-同步流程与故障恢复设计.md#故障处理)
4. 回退前暂停接收并备份新版库。停止新版宿主，恢复旧包、原插件注册、对应的 Options、原配置目录或配置卷、服务与网络规则，以及切换前的数据库快照。改过注册路径时，从备份恢复旧注册，或按记录移除新版 `spec` 后重新添加旧 `spec`。启动旧中心后核对旧历史和预期的接收路径。保留新版备份以追溯切换后收妥的 OTLP 用量。[恢复与备份](05-同步流程与故障恢复设计.md#账本迁移与备份恢复)
