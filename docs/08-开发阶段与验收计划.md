# 开发阶段与验收计划

开发顺序先验证中心原生账本入账，再验证故障恢复，最后验证管理员配置与后台状态。每次改动选择能证明预期行为和相关失败条件的检查。

## 里程碑

| 阶段 | 交付内容 | 进入下一阶段的依据 |
| --- | --- | --- |
| 1. 跑通用量链路 | 在两个独立的 Magpie 实例间打通源端游标读取、字段映射、中心 POST 与只读查询。 | 一条测试用量进入中心 `reported`，一条直接调用归为 `through`。分别核对字段、凭据与查询结果。 |
| 2. 持久进度和恢复 | 实现来源身份、锁、整页确认、原子状态写入、重放及退避。 | 在中断位置读回持久游标，验证恢复后每个预期 `rid` 恰好一条，源端模型路径在中心离线时可用。 |
| 3. 配置与诊断 | 接入 Options、Web 服务页和桌面配置桥，提供受控恢复入口。 | 每种声明支持的形态都有独立记录，能判断配置是否已保存、调度是否已生效、故障如何恢复。 |

## 按改动选择验证级别

| 级别 | 本项目的最小验证示例 | 何时停止 |
| --- | --- | --- |
| L0 静态检查 | 改 README 或字段说明时核对引用、本地链接和与目标版本的一致性。改 Skill 时另验元数据、引用和路由。 | 本次陈述或入口均有对应依据。 |
| L1 定向验证 | 成本映射只测已计价零值、缺失、正常值。按钮样式只看受影响主题、普通态及键盘焦点。 | 确认被改的输出和边界值。 |
| L2 模块集成 | 在回环模拟中心、临时状态目录或可控计时器中验证回执、落盘失败、进程中断和重放。页面读写用可控响应覆盖竞态。 | 输出、持久进度和故障后的恢复结果均符合约定。 |
| L3 宿主验收 | 宿主重载或页面桥用一套实际 Magpie。两端入账与权限常规使用隔离源和中心。使用现有节点时按验收授权范围操作。 | 在目标版本及所声明的形态观察到相关行为和失败条件。 |

各级可直接选择。发现共享调用方受影响，增加该调用方的检查。模拟与宿主表现不一致，升级到相应形态的 L3。全量回归适用于明确要求、发布验收约定或影响分析仍无法划定范围的基础改动。下表按涉及的场景选用。详见[项目分级测试规范](../.agents/skills/magpie-testing/SKILL.md)。

## 关键场景与通过标准

| 要证明什么 | 环境与操作 | 必须观察到什么 |
| --- | --- | --- |
| 两条记账路径与请求隔离 | L3 双实例，分别从源和中心调用。中断上报连接后再恢复。 | 源端继续经本机供应商完成调用，中心分别显示 `through` 和 `reported`。恢复后漏传段补齐，重放没有额外行。 |
| 空页、子批与确认边界 | L2 返回空页、后续子批失败，或预期 A、B 却给两次 A。在中心已接收但本地尚未保存时中断。 | 空页保存下一游标。回执不全或后批失败保持旧游标。重放后每个预期 `rid` 恰有一条，整页确认并成功落盘后才推进。 |
| 状态写入和恢复 | L2 使临时文件刷盘或替换失败。提供未知版本或损坏的状态文件。 | 最近持久化的游标仍可读。保留未知或损坏文件并提示恢复。进程中断与设备物理掉电分别取证。 |
| 用量口径 | L1 查字段，再按需 L3 双实例走普通、流式、失败、取消、带计量的回退及跨日记录。 | 核对 Token、状态、已知零成本与缺价、原调用日期。解释中心按尝试行计数与源端逻辑请求数的差异。 |
| 多来源与权限 | L3 在同一隔离中心接入至少两个来源，试用只读 Key 查询、写入及调用模型，再撤销其中一个上报 Key。 | 两个来源可按 `rid` 追查，重启身份稳定。只读 Key 仅可查询。撤销只影响对应来源。 |
| 配置与状态页 | L2 注入保存失败、读回失败、读回不一致和刷新乱序。声明实际桥接行为时，在目标 Web 或桌面做 L3。 | 草稿可恢复，旧响应不能覆盖最新状态。Web 可从服务页读诊断，桌面服务入口为空时仍可操作普通 Options。 |
| 宿主所有权 | L3 单实例，在旧请求仍在途时重载，另验冷启动、关页和休眠恢复。 | 旧任务退出且迟到结果无法写回，新宿主接管并仅保留一个发送循环。无人值守声明须记录关页后实际恢复用时和登录条件。 |
| 历史缺口 | L2 模拟游标失效。L3 隔离中心恢复旧备份，保留原来源身份，确认范围后重扫。 | 只采新增的来源遵守已确认历史边界。可见记录补齐且历史无重复，已清理而依赖备份的部分单独记录。 |

## 第一阶段链路验收

2026-11-25，插件 `v0.1.0` 通过 Windows Magpie `v0.1.4795` 来源端与 Docker Magpie `v0.1.4572` 中心的双端验收。[第一阶段单条用量对账](07-部署接入与运行维护.md#第一阶段单条用量对账)

| 级别与对象 | 版本与实际操作 | 观察结果 |
| --- | --- | --- |
| L0 类型与包内容 | `bun run typecheck`，`npm pack --dry-run --ignore-scripts --json` | 严格 TypeScript 检查通过。包清单包含 `server.ts` 及其运行时模块。 |
| L1–L2 映射与回执 | Bun `1.4.2`，`bun test` | 35 项通过，覆盖稳定 `rid`、已知零成本、批次字节上限、逐条回执、超时、重定向和单次认领。后续子批失败时不返回下一游标。 |
| L3 Windows 插件接入 | 宿主显示 Bun `1.4.5`。从桌面「插件 → 发现」安装本地包，在「已安装 → 选项」查看配置，另用 `magpie plugin list --json` 检查 CLI 加载。 | 桌面注册成功，初始配置为 `enabled: false`，CLI 将插件列入 `loaded`。 |
| L3 Docker 网关 | 容器内核对 `magpie --version`、`/config` 挂载和端口映射。从 Windows 访问原生网关，从容器内回环读取起始游标。 | `/config` 为读写绑定挂载。Windows 可达网关，未带 Key 返回 `401`。容器内返回带 `next_cursor` 的空页。 |
| L3 来源请求与插件回执 | 用来源测试模型 Key 的 ID 筛选 `cursor=now`。发起一次合成模型调用后沿用筛选条件续读，在桌面 Options 保存单次发送配置。 | 模型返回 `200`。来源页恰有一条 `origin=gateway` 的已计量记录。插件结果为 `confirmed`，回执 `accepted=1`、`skipped=0`。 |
| L3 两类中心用量 | 用中心专用模型 Key 直接调用一次，返回 `200`。用独立只读 Key 读取 `period=all` 汇总、按该模型 Key 查询 `through`，沿上报前的游标续读 `reported` 并精确匹配 `rid`。 | 三次读取均为 `200`。按本次标识查到一条 `through` 和一条 `reported`，各自的原调用时间、供应商、模型、Token 和状态均与对应来源一致。 |
| L3 只读权限 | 用同一只读 Key，复用已入账的 `rid` 探测上报接口，用无效 JSON 探测模型路由。 | 两项均返回 `403` 和 `gateway_key_read_only`。 |

本轮核对了两端版本的游标、上报接收、逐项回执与去重实现。持久游标、重放和中断恢复在第二阶段独立验收。[中心用量接口](https://github.com/yetone/magpie/blob/v0.1.4572/internal/gateway/usage_api.go) · [上报回执](https://github.com/yetone/magpie/blob/v0.1.4572/internal/gateway/usage_ingest.go)
